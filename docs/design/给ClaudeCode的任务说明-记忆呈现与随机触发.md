## 已确认的现状问题（不用重新验证，可以直接当结论用）

1. `getMemoryMenu()` 每轮都会调用一次 `/search`，固定取 `n=8`，只要检索到结果就 100% 注入到最新一条 user 消息前面，没有任何"要不要展示"的判断。
2. 现在的排序（`memories.sort(key=lambda m: (-is_core, -score))`）没有相关度下限，哪怕是排名靠后、相关度很低的记忆，只要凑够 8 条也会被展示。
3. 呈现格式是结构化的"标签+bullet+字段"：`[相关记忆目录]\n- [日期 类型] 摘要…`。这种格式本身会让 LLM 把它当成"一份需要处理/汇报的数据"，而不是"一闪而过的念头"——即使 prompt 里写了"不要沉溺过去"，格式本身已经在暗示相反的事。
4. `access_count` 在 `search_memories()` 里是每次 `/search` 命中就 +1，而 `getMemoryMenu()` 每轮都在调 `/search`。也就是说，现在的 access_count 把"只是被展示在目录里"和"被真正 recall 调用"混在了一起统计。如果以后要基于访问频率做疲劳度/冷却，这个字段现在的口径是脏的，不能直接拿来用，需要先想清楚要不要拆分统计口径，或者引入一个新的、专门统计"被展示次数"的字段。

## 这次的目标（原则）

1. 平时大部分时候不展示任何记忆片段，只在少数时候、恰到好处地"浮现"一点点。
2. 展示与否，不应该是"检索到就展示"，而应该经过一次"要不要开放回忆"的随机判断，再看相关度是否够格。
3. 即使够格，也不是固定展示 N 条，而是加权随机抽 0~2 条，并且要避免同一条记忆被短时间内反复展示（需要某种"最近展示过，这一轮降低概率"的冷却机制）。
4. 允许有一个很小概率的"无由来浮现"通道：不看当前话题相关度，从"很久没被想起、但情感强度高或被标记为核心记忆"里随机挑一条，用来模拟"不知道为什么突然想起"的感觉——这个通道和"按相关度触发"是两条并行路径，不要合并成一套逻辑。
5. 呈现格式从"标签+清单"改成更接近内心念头的自然语言短句，去掉明显的表格感（比如不要用 `[日期 类型] 摘要` 这种字段拼接的样子）。
6. 引导 LLM 理解这类内容的文案，应该放进稳定的 systemPrefix（会被 prompt cache 缓存的部分），不要每轮重复注入，因为这是"如何理解这类内容"的长期原则，不是每轮都变的动态信息。
7. 文案措辞上有一条特别的分寸要守住：只描述"存在共同经历过的痕迹"，不要描述"这段经历意味着什么关系"。也就是说可以说"这是我们曾经共有的一点痕迹"，但不要出现类似"这是你的朋友/伴侣说过的话"这种替它预设关系角色的表达——关系怎么理解，应该留给它自己判断，不要被文案预先定型。
