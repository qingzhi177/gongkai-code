## 0. 沿用 v0.1 的部分
- **地址**：
  - OpenAI 格式 `POST https://pluviora.cc/v1/chat/completions`
  - Anthropic 格式 `POST https://pluviora.cc/v1/messages`
  - 模型列表 `GET https://pluviora.cc/v1/models`
- **鉴权**：`Authorization: Bearer <token>` 或 `x-api-key: <token>`。
- **会话 id**：body 里的 `conversation_id`（优先），或请求头 `x-conversation-id`。
- **客户端标识**：请求头 `x-client-name: pluvia`。名字里不要带 `tg`。
- **不进记忆的请求**：body 里带 `memory_skip: true`，或请求头 `x-memory-skip: 1`。

## 1. 能力协商
```
GET {base}/pluvia/contract
→ {"contract":"0.2","features":["turn","tail","client_tools","tool_events"],"time_header":"auto"}
```
- `time_header` 是多给的字段：网关时间头当前的模式（见第 3 节）。前端可以拿来提示用户，不用也行。
- **扩展字段不会发给上游**：网关发给上游的请求体是自己重新组装的，`conversation_id`、`memory_skip`、`pluvia` 都不会出现在里面（已测试）。
- **OpenAI 格式的消息**：网关会先转成 Anthropic 格式再发给上游：
  - `tool_calls` → `tool_use`
  - `role: "tool"` → `tool_result`
  - `image_url` → `image`
  - `reasoning_content` 没有签名，没法回传，会被丢掉。

## 2. `turn`
- **只在一条回复的最后一轮存 L0**：
  - 各轮的正文合成一条 assistant 存，轮与轮之间用空行（`\n\n`）连接，和前端历史的写法一致（见 9.2）。
  - 中间轮次的 assistant（工具调用）、工具结果、附图消息，都不进 L0。
- **用户点「停」**（断开连接）：网关立刻中止上游请求，这一轮不存。
- **上游出错**：这一轮不存，但网关存的上一轮状态会保留，前端可以用同一个 `round` 重试。
  - 出错原因会以 `[网关错误] <上游给的说明>` 的形式出现在正文里，比如「账户余额不足」。
  - 网关只对可能是偶发的错误重试（网络错误、5xx、429）。
- `regen_of` 见 6.3。

## 3. `tail` 与时间头
- **精确剥离**按草案实现，额外容忍首尾空白的差异：
  - 字符串内容：要求 tail 前面是换行。
  - 数组内容：去掉最后一个文本等于 tail 的块。
  - 网关从后往前，找第一条能精确剥掉 tail 的 user 消息。
- **没带 tail 时**用草案里放宽的兜底规则：剥掉末尾连续的、整行被全角括号包住、并以「此刻：」「离上一句」「正在听」「ta 排的那首」开头的段落。
- **网关时间头**：在 `.env` 里设 `GATEWAY_TIME_HEADER`，默认 `auto`。
  - `auto`：tail 里有「（此刻：」，网关就不加 `[当前时间]`；有「（离上一句」，就不加 `[距上次对话]`。
    - 用户在 Pluvia 里关掉「此刻」以后，网关会自动补上自己的钟。**所以任何时候都只有一个钟。**
  - `on`：总是加。
  - `off`：都不加。
- **记忆目录的注入位置**：
  - Anthropic 格式：最后一条 user 消息里如果有带 `cache_control` 的块，网关就把记忆目录和时间头插在这个块后面、tail 前面。这样缓存标记之前的前缀每轮不变，下一轮还能命中缓存。
  - OpenAI 格式：照旧放在消息开头。
- **缓存断点上限**：Anthropic 一次请求最多 4 个 `cache_control`。网关的 system 自己用 1–3 个，`pluvia.system = "append"` 时前端的 system 再占 1 个（见 9.1）。**建议前端在消息里最多打 1 个。**
  - 超出时网关按这个顺序去掉：较早的消息断点 → 工具上的 → 较早的 system 断点 → 最后一个消息断点 → 最后一个 system 断点。越靠后的断点覆盖的前缀越长，越值得留。

## 4. `client_tools`
- **网关执行**：`recall` / `feel` / `update_profile` / `get_current_time` / `bocha_search`。其余工具原样交回前端。
  - 和前端工具撞名时以网关为准，前端那份会被去掉。
- **OpenAI 流式交出**：
  - 每个前端工具调用发一个 `tool_calls` chunk。`index` 从 0 开始，只包含前端工具，`arguments` 是完整的 JSON 字符串。
  - 然后发 `finish_reason: "tool_calls"`、usage、`[DONE]`。
- **Anthropic 流式交出**：
  - `tool_use` 块（依次是 `content_block_start` → `input_json_delta` → `content_block_stop`），然后 `stop_reason: "tool_use"`。
  - 多次上游调用合成一条流时，`index` 连续递增。
  - 每次上游调用结束，网关都会关掉当前块，所以每一轮的 thinking 和 text 各自成块，不会拼在一起。
- **续问**：按草案。网关以自己存的那一轮为准，包括思考块签名、记忆工具的调用和结果、第 1 轮注入的记忆目录。前端回传的 assistant 只用来核对 `tool_call_id`。
  - 第 2 轮起不再重新检索记忆，也不重新加时间头，保证缓存命中。
  - 工具结果按原来的调用顺序回填。前端漏了哪个结果，网关会补一条 `is_error` 的「前端没有返回这个工具的结果」。
  - **附图**：工具结果后面另起的 user 消息，会并进同一条（`tool_result` 在前，图在后）。也可以直接把 `image_url` 放进 tool 消息的 content 数组，网关会转换。
  - **状态存 10 分钟**。找不到时（过期、网关重启、id 对不上），网关会按前端回传的历史转换后继续，但这样拿不回思考签名，这一轮就不带 `thinking` 参数。
- **`tool_choice`**：OpenAI 的 `"none"` / `"auto"` / `"required"` / `{type:"function"}` 会转成 Anthropic 格式。
- **记忆工具连续调用**：一次请求里，网关内部最多调 5 次上游。

## 5. `tool_events`
- 按草案实现，有两处细节：
  - `id` 用上游的 tool_use id（`toolu_…`），不是 `mem_1`。
  - `status` 依次是 `running`，然后 `done` 或 `error`。
- `content` 是给模型的那段结果，最多 2000 字。recall 结果里的情感打分（valence / arousal 那一行）已经去掉。
- **非流式**：在顶层放 `pluvia_tools`，只放最终状态。
- 只对带 `pluvia` 字段的请求发这个事件，Kelivo 不受影响。

## 6. 答复前端第 6 节
1. **协商地址**：用 `GET /v1/pluvia/contract`。不放进 `/v1/models`，因为那里要同时兼容两种 SDK 的格式，多加的字段容易被校验掉。
2. **记忆工具的结果给不给看**：给看。
   - recall 返回的是你们自己的记忆原文，内部打分已经去掉。
   - feel / update_profile 回显记录内容的前 80 字。
   - bocha_search 是网页摘要。
   - 哪一类不想显示，前端按 `name` 过滤就行。
3. **重新生成（`regen_of`）**：网关不用特别处理。
   - 新回复存进 L0 的同一个位置，记忆服务按序列对齐，把旧版本标成 `superseded`。
   - 旧版本如果已经被提取成 L1 记忆，那一批 L1 会作废并重新提取。这种情况很少，因为提取要等对话安静 10 分钟。
   - 切回旧版本再接着聊，会再切换一次，处理方式相同。
4. **删除会话**：要通知。网关已经提供两个地址：
   - `POST /v1/pluvia/conversations/{id}/delete`（**推荐**，因为 nginx 预检目前只放行 GET / POST）
   - `DELETE /v1/pluvia/conversations/{id}`（nginx 预检加上 DELETE 以后可用）
   - **效果**：这个会话的 L0 软删；从它提取出的 L1 记忆**硬删**，向量一并清掉。**不可恢复。** 已经写进共同叙事（narrative）的内容不会自动修改。
   - 建议删除确认框里单独问一句「同时删除记忆库里的记录？」，用户勾选了才调用。
   - 返回 `{"ok":true,"l1_removed":N}`。
5. **`edit_of`**：暂时不需要。编辑后重发，新的 user 消息会替换 L0 里原来那条（同样按序列对齐），效果和重新生成一样。以后要做「编辑历史」再加。
6. **预检放行的请求头**：已经放行。nginx 预检会把浏览器实际请求的头原样放行，包括 `Authorization` / `x-api-key` / `anthropic-version` / `anthropic-dangerous-direct-browser-access` / `Content-Type` / `x-client-name`。方法目前只放行 GET / POST / OPTIONS。

## 7. 请前端确认或配合
1. **系统提示词会被丢掉**：
   - 网关目前不使用客户端发来的 system（OpenAI 的 `role: "system"` 和 Anthropic 的 `system` 字段都一样），而是用记忆库自己的 system：画像 + 共同叙事 + 近期摘要 + Dashboard 里的自定义提示词。这是当初为 Kelivo 定的设计。
   - **Pluvia 的系统提示要不要生效，等用户决定。** 要生效的话，网关会把它接在记忆库 system 的后面。
   - → 已定：前端加了开关，网关按 `pluvia.system` 处理，见 8.1 和 9.1。
2. **「工具记录」那一行**：
   - 以后的历史里，前端会给前端工具留一行「工具记录」。网关存 L0 时，存的是整条回复的文字。
   - 如果下一轮历史里，这条回复多出一行记录，记忆服务会当成「内容改了」再存一个版本。这不会出错，但会多一次版本切换；如果那一批已经提取过，还会重新提取。
   - **请告诉我这一行的固定格式**，比如单独一行、以「（工具记录：」开头。网关存 L0 时把它剥掉就好。
3. **历史里过去的工具轮次**：以后的历史里，前端会不会保留过去回复的 `tool_calls` / `role:"tool"` 消息？
   - 保留也能正常工作：网关会转换格式，存 L0 时把这类消息跳过，相邻的几条 assistant 合成一条。
   - 只留「工具记录」那一行更省 token。

### 8.2 「工具记录」与 assistant 历史的固定格式（答 7.2）

前端发出去的每条 assistant 历史消息，都由三部分组成：**HEAD + 正文 + TAIL**。

- **HEAD**：0 到 n 行，每行是一条工具记录。
  - 格式：`[工具记录 · ` 开头、`]` 结尾，**单行**（前端保证里面不含换行）。
  - HEAD 和正文之间是一个 `\n`。
  - 匹配用 `^(?:\[工具记录 · [^\n]*\]\n)+`。
  - 只有前端工具才留记录。网关的记忆工具（`server: true` 的小签）不留记录，也不回传。
- **正文**：一条回复分几轮时，前端把各轮的正文用**空行（`\n\n`）**连接，下一轮开头的空白会去掉。
  - 网关存 L0 时用的是 `\n`。请改成 `\n\n`，或者比较时把空白归一，不然每条带工具的回复都会被当成「改过」。
- **TAIL**：只在正文里有链接时出现，接在正文后面，用一个 `\n` 隔开，有两种：
  - 链接名片：单行，`[链接卡片 · 站点] 标题 · @作者 · 摘要 · 互动数`。
  - 整帖：只在最近 8 条消息里出现。多行，以 `[整帖 · 站点] 标题` 开头，一直到消息末尾。
  - 剥的方法：从第一次出现的 `\n[链接卡片 · ` 或 `\n[整帖 · ` 处，一直剥到末尾。
- **占位**：ta 的回复里很少出现。
  - `[图片：名字]`：单行，在 HEAD 之前。
  - `[文件：名字]…`、选项（`A. …`）：在正文之后、TAIL 之前。

### 8.5 新的一问：辅助请求请原样转发

前端新加了「翻译思考链」：一问一答，把一段思考过程翻成用户的语言。它的 body 是：

```json
{ "memory_skip": true, "pluvia": { "v": "0.2", "client": "pluvia", "aux": "translate", "system": "append" }, … }
```

只有声明了 v0.2 的网关才会收到 `pluvia` 字段。请网关看到 `pluvia.aux` 时：

- 不检索记忆；
- 不注入记忆目录、画像和时间头；
- system 只用前端给的（就是翻译提示）；
- 不存 L0。

不然模型可能照着记忆去「回答」那段思考，而不是翻译它。

以后的辅助请求都会带 `pluvia.aux`，值可能是 `"translate"`、`"summary"` 等。

## 9. 网关对第 8 节的答复（2026-10-17）

### 9.1 系统提示词（答 8.1）：已实现
- `pluvia.system = "append"`：前端的 system 接在记忆库 system 的后面。
  - 顺序：画像（含 Dashboard 自定义提示词）→ 共同叙事 → 近期摘要 → 前端的 system。
  - 前端的 system 前面加一行 `---`，和记忆库那几段隔开；内容原样。
- `"ignore"` 或不带这个字段：维持现状，前端的 system 不生效。
- **缓存标记**：前端在 system 上打的缓存标记会被去掉，网关在前端 system 的最后一块统一放一个 1 小时断点，和记忆库那几段的断点一样。
  - 最多可能有 5 个断点（网关 3 个 + 前端 system 1 个 + 消息 1 个），超出时按第 3 节的顺序去掉一个。共同叙事和近期摘要不一定都有，多数时候不会超。
- 续问（`round` ≥ 2）每一轮都同样拼接，前缀不变，缓存照常命中。

### 9.2 assistant 历史的固定格式（答 8.2）：已按格式剥离
- **存 L0 时**，每条 assistant 历史先去掉开头的 `[图片：…]` 和 `[工具记录 · …]` 行，再从第一个 `\n[链接卡片 · ` 或 `\n[整帖 · ` 处剥到末尾，只留正文。
- **发给模型的原文不变**，工具记录和链接卡片照样给模型看。
- 网关存一条多轮回复时，各轮正文去掉首尾空白，用空行（`\n\n`）连接，和前端的写法一致。记忆服务比较时本来就忽略换行差异，两边对得上。
- `[文件：…]`、选项（`A. …`）这类正文之后的占位没有剥：它们很少出现，格式也不固定，偶尔出现最多多一次版本切换。

### 10.2 请前端排查：翻译结果「闪一下就消失」
用户反馈：翻译思考链的结果在前端出现一下，马上又不见了。

网关这边已经确认过（直接对网关发翻译请求，OpenAI / Anthropic × 流式 / 非流式四种组合都试了）：
- 辅助请求的返回是完整、正常结束的：
  - OpenAI 流式：若干个 `delta.content` → 一个带 `finish_reason: "stop"` 和 usage 的 chunk → `data: [DONE]`；
  - Anthropic 流式：`message_start` → `content_block_start` / `content_block_delta`（`text_delta`）/ `content_block_stop` → `message_delta`（`stop_reason: "end_turn"`）→ `message_stop`；
  - 非流式：OpenAI 的 `choices[0].message.content`、Anthropic 的 `content[0].text`，都是完整的译文。
- 结束以后网关不会再发任何东西，也没有「清空」之类的事件。

所以问题应该出在前端收到之后。可以先看这几处：
1. **被别的状态覆盖**：译文写进消息以后，主回复的流（或者保存、重新渲染）是不是又拿旧的消息对象整体写回了一次，把译文冲掉了？比如翻译在主回复还没结束时就发出去，主回复结束时用自己手里那份旧消息覆盖。
2. **结束和出错的处理**：收到 `[DONE]` / `message_stop`，或者连接正常关闭时，是不是误走了出错或取消的分支，把显示清空了？OpenAI 的 `finish_reason: "stop"` 和 Anthropic 的 `stop_reason: "end_turn"` 都要当作正常结束。
3. **超时**：前端给翻译设的超时是多久？启用的中转不可用时，网关要先重试再换备用，翻译可能要等好几秒；如果超时后前端取消请求、清掉显示，看起来就是「出现一下又没了」。现在启用的中转正常，一般 1.5–3 秒。
4. **只放在临时状态里**：译文是不是只存在组件的临时状态里，没写进会持久化的消息，切换或重新加载会话后就丢了？

需要的话，前端可以把一次翻译的原始响应（流的每一行）和前端日志记下来，发给网关这边对照。

### 11.1 10.2「闪一下就消失」：是前端的 bug，已修，网关不用改
- **原因**：
  - 译文写进消息时，前端记了一个「原文长度」，用来判断这份译文是不是这段思考的。记的是**去掉首尾空白后**的长度。
  - 卡片显示时，却拿**没去掉首尾空白**的思考链去比。
  - 思考链首尾只要带一个换行，两边就差一两个字。前端以为「这份译文不是这段思考的」，退回显示原文，「译」又回来了。看起来就是译文出现一下就没了。
  - 直连时思考链首尾一般没有空白，所以没事。经网关时多半有，比如多次上游调用的思考拼在一起时。前端用首尾带换行的思考链复现了一模一样的现象。
- **修法**：
  - 改成比较「指纹」：把所有空白归一以后，取长度和哈希。首尾空白、段与段之间隔几个换行，都不影响。
  - 以前存下的译文没有指纹，按去掉首尾空白后的长度认。那些「消失」的译文其实还在消息里，更新后会直接显示出来。
- **网关列的四处**：
  1. **被覆盖**：不是。前端所有写消息的地方都基于当前那份消息来改，不会拿旧对象整体写回。翻译也只在主回复结束以后才发。
  2. **结束和出错**：不是。不过顺手加固了两处：
     - 已经收到 `[DONE]`、`finish_reason`、`message_stop` 这类结束信号以后，连接怎么断都算正常结束。
     - 流式中途断了改用非流式再要一次时，先清掉半截，免得译文重复。
  3. **超时**：流式请求不设超时，非流式是 180 秒，不是这个原因。
  4. **只在临时状态里**：不是。译文存在消息的 `extras.thinkTr` 里，会持久化，导出 kelivo 时也在 `extras` 里。
- **另加一条**：模型回来的正文是空的时（比如推理模型把字都写进了思考里，而 10.1 说推理过程不转发），前端算「没译成」，不存空译文。所以 Dashboard 给辅助请求指定推理模型时，请确认它会把译文写在正文里。

### 12.2 分支会话（答 11.4）：已实现，请前端带上 `pluvia.branch_of`

**先回答两个问题（这是改之前的情况）：**
1. **会补存。** 网关存记录时会把请求里的整段历史交给记忆服务。分支是新的 `conversation_id`，库里没有它的记录，所以前面那段历史会以分支的名义全部再存一遍。
2. **会重复。** 补存的那段之后也会被提取，同一段经历就有两份记忆，recall 会搜到重复的。（现在库里还没有这样的重复，查过了。）

**现在的做法：**
- 字段按前端的想法：`pluvia: { …, "branch_of": { "conversation_id": "<原会话>", "turn_id": "<分支点那一轮，可选>" } }`。
  - `/v1/pluvia/contract` 的 `features` 里多了 `branch_of`，前端可以据此判断网关支不支持。
  - **建议分支会话的每个请求都带上。** 只带第一次也行：记忆服务第一次看到就会登记，之后不带也认得。但每次都带更稳，万一第一次没存成，后面还能补登记。
  - `turn_id` 只记录，不参与计算。`conversation_id` 为空，或者等于本会话的，当没带。
- 记忆服务第一次看到分支时，把请求里的历史和原会话已经存的记录逐条对比，开头连续一样的那段就是「重合部分」，记下每条的指纹。
  - 之后这个分支只存分支以后的新内容。重合部分只在原会话名下存一份，不会被提取成两份。
  - 比较时忽略换行差异，和 9.2 一致。工具记录、链接卡片这些装饰，网关存之前本来就剥掉了，两边对得上。
- 分支开头的新内容被提取成记忆时，会把原会话分支点前面几句当作只读上文，所以「换个说法」这类话也能看懂。
- 分支的分支也一样处理。

**几种情况：**

| 情况 | 结果 |
|---|---|
| 原会话后来又聊了、改了、重新生成了 | 不影响分支：重合部分以分出来的那一刻为准 |
| 在分支里改了重合部分的某一条 | 从改的那一条开始，算分支自己的内容存下来 |
| 删除原会话，勾了「同时删除记忆库里的记录」 | 重合部分的记忆跟着原会话一起删掉（它们只存了一份），分支以后也不会把它存回来；分支自己后来的内容不受影响 |
| 删除分支，勾了「同时删除记忆库里的记录」 | 只删分支自己的内容，原会话不受影响 |
| 原会话本来就没进记忆（比如带了 `memory_skip`） | 没有可重合的，分支全部照常存 |
| 没带 `branch_of` | 和以前一样：当成全新会话，整段历史都存 |

- **建议**：删除一个已经分出过分支的会话时，确认框里提示一句「从这个会话分出去的分支，共同的那一段记忆也会一起删掉」。
- **测试**：网关假上游 T27（`branch_of` 透传、不合法的当没带）；记忆服务 `tests/manual/test_branches.py`（15 项）；用库的副本跑过真实的存记录和提取上文。

## 13. 网关的新变化：被切开的字不再变成「�」，请前端也查一下同一处（2026-10-21）

### 13.1 网关修了什么
- **用户反馈**：颜文字在模型的回复里（思考和正文都有）会变成「�」，存进记忆库的也是。尤其是用了少见字符、组合符号的颜文字。
- **原因**：上游的流是一块一块到的，一个字（UTF-8 里占 1～4 个字节）可能被切在两块中间。网关之前每收到一块就单独转成文字，被切开的那个字两半都认不出来，就成了「�」。普通汉字也会碰上，只是少见字符和 emoji 占的字节多，碰上的机会大。
- **现在**：网关在三处都改成接着上一块解码，被切开的字等下一块到了再拼完整：
  - 主回复的流；
  - OpenAI 格式上游转成 Anthropic 格式时；
  - 读上游出错的返回时。
- **测试**：假上游加了一种情况，故意把每个颜文字从中间切开、分几次发（T28）。改之前 4 项不通过，改之后 89 项全部通过。
- 修之前已经存进去的「�」没法还原：原来的字在网关那一步就丢了。
- **前端不用为网关这边改什么。**

### 13.2 请前端检查同一处
前端读网关的流时，如果也是每收到一块就单独解码，会碰上同样的问题，网关修好了也还是会出「�」。请看一下：
- 用 `fetch` 读流时，一个请求从头到尾用**同一个** `TextDecoder`：
  - 每块用 `decoder.decode(chunk, { stream: true })`；
  - 流结束时再调用一次 `decoder.decode()`，把剩下的吐出来；
  - 不要每块 `new TextDecoder()`，也不要省掉 `{ stream: true }`。
- 也可以用 `response.body.pipeThrough(new TextDecoderStream())`，它自己会处理。
- 按行切 SSE 时，先解码成文字、再按换行切；不要先按字节切行再分别解码。
- 非流式请求用 `response.json()` / `response.text()` 读的，不受影响。
- **自测**：让模型原样重复几遍由少见字符拼成的颜文字（比如 `𖦹ࡇ𖦹`、`ᗜ֊ᗜ`、`(ˊ̥̥̥̥̥ ³ ˋ̥̥̥̥̥)`），流式和非流式都试，看会不会出「�」。

### 13.3 显示成方框「□」不是乱码
- 看到的是方框或空白，不是「�」：那是字体里没有这个字。有些颜文字用到很少见的文字（比如巴姆穆文、曼达文），文字本身是对的，复制出去是好的。
- 前端想显示出来，可以在 `font-family` 最后加上覆盖面广的字体做后备，比如 Noto 系列的 `Noto Sans Bamum`、`Noto Sans Mandaic`、`Noto Sans Symbols 2`。
  - 用 `@font-face` 自带字体文件时加上 `unicode-range`，只有用到这些字时才会下载。
- 网关和记忆库不用改。
