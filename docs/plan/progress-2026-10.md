- 按会话分段（间隔 > 30 分钟或满 40 条切段），每段带前 6 条只读上下文。

## 2026-10-17（凌晨）· Pluvia 接入约定 v0.2

完整约定见 [`pluvia-gateway-contract.md`](pluvia-gateway-contract.md)。以后主要用 Pluvia，Kelivo 的路径保留不动。

### 网关新增
- `GET /v1/pluvia/contract`：能力协商，声明 `turn` / `tail` / `client_tools` / `tool_events` 四项。
- **turn**：一条回复只在最后一轮存 L0，各轮文字合成一条；用户点「停」时中止上游、不存。
- **tail**：按前端给的「此刻」原文精确剥离，没带时用放宽的兜底规则。
- **client_tools**：网关只执行 5 个记忆工具，前端工具交回前端执行。交出时这一轮的上游状态（含思考签名、记忆工具结果）存 10 分钟，续问时原样接回，缓存可命中。
- **tool_events**：记忆工具的执行过程以 `pluvia_tool` 事件推给前端显示，recall 结果去掉了内部打分。
- **删除会话**：`POST /v1/pluvia/conversations/{id}/delete`（另有 DELETE 写法）。L0 软删，对应 L1 硬删。
- **时间头开关**：`.env` 里的 `GATEWAY_TIME_HEADER=auto|on|off`，默认 auto。前端带了「此刻」，网关就不再加 `[当前时间]`；带了「离上一句」，就不再加 `[距上次对话]`。
- **顺带修复**（对所有客户端生效）：
  - 上游报错时，前端能看到真实原因（如「账户余额不足」）；4xx 不再白白重试 3 次。
  - 工具循环回传上游时，保留被加密的思考块（`redacted_thinking`）。
  - OpenAI 格式的 `tool_choice` 会转换成 Anthropic 格式。
  - `cache_control` 超过 4 个时，自动去掉最早的几个。
  - `role:"tool"` 的消息不再进 L0。

### 测试
- `tests/manual/pluvia_contract/run.sh`：假上游 + 假记忆服务 + 端口 3999 上的临时网关，49 项全部通过（含 Kelivo 路径不变的检查）。
- 线上：Pluvia 格式的真实请求正常返回。

### 发现的问题
- **上游中转站余额已用完**，所有请求现在返回 403。充值后恢复。
- 测试用的一条极短请求（带 `tool_choice: "none"` 和一个前端工具），中转站报了 **77,753 个输入 token**，同样大小的请求平常约 3 千，原因未明。充值后用同一条请求、分别带与不带 `tool_choice` 对比一次；如果确实和 `tool_choice: "none"` 有关，就让网关在第 5 轮改成不发工具列表。

## 2026-10-18（凌晨）· Pluvia 约定第 8 节 + 真实模型测试

前端在约定第 8 节答复了第 7 节的三件事，另外提了辅助请求（8.5）。网关的答复写在约定第 9 节。

### 网关新增
- **前端系统提示词**（8.1）：`pluvia.system = "append"` 时，Pluvia 的 system 接在记忆库 system 后面，统一放一个 1 小时缓存断点；默认 `ignore`，行为不变。
- **存 L0 时剥掉前端加的装饰**（8.2）：assistant 历史开头的 `[图片：…]` / `[工具记录 · …]` 行，以及末尾的 `[链接卡片 · …]` / `[整帖 · …]`。发给模型的原文不变。多轮回复的各轮正文改用空行连接，和前端一致。
- **辅助请求**（8.5）：带 `pluvia.aux` 时，不检索、不注入记忆库的 system / 目录 / 时间头，不带记忆工具，不存。
- **缓存断点裁剪**：把 system 断点也算进去，按「较早的消息 → 工具 → 较早的 system → 最后一个消息 → 最后一个 system」的顺序去掉。
- 没有工具时请求里不再带 `tools` 字段。
- 每次请求在 `gateway.log` 记一行 `[UPSTREAM]`：只记 system、消息、工具各占多少字符，不记内容。用来核对中转站报的 token 数。

### 测试
- 假上游：`tests/manual/pluvia_contract/run.sh`，58 项全部通过。
- 真实模型：`tests/manual/pluvia_contract/real_smoke.js`，7 组全部通过（全部带 `memory_skip`，L0 里没有留下测试数据）：
  - 前端工具两轮：Anthropic 格式，带 thinking，签名能回传；OpenAI 格式。
  - 辅助请求（翻译）。
  - 前端 system 拼接后，模型能看到里面的内容。

### 发现
- **上次报的 77,753 token 没有复现**：同一条请求现在合计约 2.2 千 token。
- **中转站的 usage 数字不可信**：每条请求「读缓存」的数量，几乎正好等于上一条请求的总量；就算第一块 system 的内容完全不同也是这样，真实的 Anthropic 缓存不会这样。中转站很可能自己估算用量，77k 那次大概也是它的统计问题。
- **中转站会间歇性丢掉 system 提示词**：
  - 00:10–00:14 这几分钟里，直接（不经过网关）发给中转站的请求，大多数看不到 system 提示词，模型自称「一个 AI 开发环境，可以帮你写代码」。
  - 00:15 以后恢复，各种写法都是 10/10。
  - 这是中转站把请求转到了会替换提示词的通道，不是网关的问题。陪伴时 ta 如果突然「不认识你」、口吻变成编程助手，多半是这个原因。
  - 新增 `scripts/check_relay_system.py`，直接测中转站有没有把 system 送到，随时可以跑。

### 多中转自动切换（failover）
- Dashboard 里配了 4 个聊天中转：cam（当前启用）、openrouter、fuse、fusev1。以前网关只用当前启用的一个，cam 余额用完那次所有对话都直接失败了。
- 现在当前中转出错时，网关按顺序改用下一个：
  - 会切换的错误：网络错误、超时、5xx、429，以及 401/402/403/404（余额不足、密钥失效、地址不对）。
  - 不切换的情况：参数错误（400），换了也没用；已经开始往前端输出之后才出错的，也不切。
  - 模型名自动对应，比如 `claude-opus-4-6` ↔ `anthropic/claude-opus-4.6`；没有同款模型的中转直接跳过，不会悄悄换成别的模型。
  - 全部失败时，正文里列出每个中转各自的失败原因。
- 记忆服务新增 `GET /config/chat_targets`（只给本机网关用）。
- `.env` 设置：`GATEWAY_FAILOVER=on|off`（默认 on）；`GATEWAY_FAILOVER_ORDER=fuse,openrouter`（只用列出的几个、按这个顺序；不设就按 Dashboard 里的顺序）。
- 实测：临时网关里故意把 cam 的密钥改错，cam 返回 401，网关马上改用 openrouter 回答。
- **顺带修了一个暴露**：以前有 Dashboard 密码的人，能通过 `/api/config/current` 拿到当前中转的明文密钥。现在 `/api` 代理拦掉了 `/config/current` 和 `/config/chat_targets`，网关自己在本机直接调用，不受影响。
- `check_relay_system.py` 改成逐个测所有聊天中转（要用记忆服务的 Python 运行）。这次 4 个全部正常；fuse 在 Cloudflare 后面，会拦 Python 默认的 User-Agent（403 error code: 1010），脚本已经自带 UA，网关用的 axios 不受影响。

## 2026-10-18（凌晨）· Phase 1：统一时间（UTC）

### 问题
- VPS 的时区是北京时间。代码里有的地方用 `datetime.now()`（北京时间）写库，有的用 `CURRENT_TIMESTAMP`（UTC），读的时候又当成同一种。
- 后果：
  - recall 给模型看的日期直接截 UTC，北京时间凌晨 0–8 点的事被标成前一天；
  - 网关的模糊时间把 UTC 当本地时间解析（差 8 小时），而且按「过了几个 24 小时」算，昨天傍晚的事会被说成「今天早些时候」；
  - 导入接口把带 Z 的 UTC 时间也减了 8 小时，还存成带 T 的格式，和其它行排序对不上；
  - 近期摘要要求「每天发生的事各自成句」，可喂给模型的对话里没有日期；提取提示词要求「用具体日期」，模型也不知道今天是哪天。
- 现有数据都是实时聊天写入的，本来就是 UTC，**不用迁移旧数据**。

### 改法
- 新增 `services/memory-service/timeutil.py`：存储一律用 UTC 的 `YYYY-MM-DD HH:MM:SS`（和 SQLite 的 `datetime('now')` 一致）；只在给人或模型看的地方，按 `.env` 的 `USER_TZ`（默认 `Asia/Shanghai`）换算。
- 记忆服务：所有 `datetime.now()` 写库的地方改成 UTC；导入时不带时区的时间按用户时区理解；叙事素材的日期、思考记录的显示改成北京时间；近期摘要的对话在换天处插一行「—— 10月18日 周日 ——」。
- 提取：每段对话前加一行「这段对话发生在 2026-10-18 00:12 至 00:45（北京时间）」。冒烟测试里，「下周三要去面试」被提取成了「她10月21日要去面试」。
- 网关：
  - 新增 `parseStoredTs` / `fmtLocal`，按 `USER_TZ` 换算；
  - recall 结果显示北京时间的日期和时刻；
  - 模糊时间按北京时间的日历天算（今天早些时候 / 昨天 / 前天 / 最近……）；
  - 时间头和 get_current_time 带上周几。

### 测试
- `tests/manual/test_timeutil.py` 13 项；网关假上游 65 项（新增：recall 里的时间换算成北京时间）；`phase0_smoke.py` 全部通过。

## 2026-10-18（凌晨）· Phase 1：数据库连接统一 + 迁移框架

### 问题
- 建表、加列的代码散在两处（记忆服务的 `init_db()`、提取脚本的 `ensure_columns()`）。每次启动都把几十条 `ALTER TABLE` 试一遍，靠报错判断列是不是已经有了；没有版本记录，看不出库现在是什么结构。
- 80 多处各自 `sqlite3.connect`，等锁时间是默认的 5 秒。记忆服务、cron 提取、导入同时写库时，更容易碰到 `database is locked`。
- 整个库一个索引都没有，按会话取对话、找未提取的消息都是全表扫描。
- 顺带发现：全新的空库第一次启动时，`thinking_records.full_reply` 列加不上（加列写在了建表前面），要第二次启动才补上。

### 改法
- 新增 `services/memory-service/db.py`：
  - `connect()`：统一的连接入口，等锁最多 10 秒。记忆服务里是 `get_conn()`；提取脚本、导入导出也都改用它（共 86 处）。

## 2026-10-18（凌晨）· Phase 1：任务表 + worker

### 为什么
- 提取靠 cron 每 10 分钟跑一次脚本；摘要、叙事、画像靠记忆服务进程里的定时器或后台协程。失败了只留一行日志，没有重试，也没有地方看。
- Dashboard 的「立即提取」会另起一个进程，和 cron 撞在一起时，同一段对话可能被提取两次。
- 这些任务都是动辄几十秒的大模型调用，跑在记忆服务进程里，会和聊天路径抢资源。

### 改法
- 迁移 `003_pipeline_jobs`：任务表 `pipeline_jobs`，加上 worker 心跳表 `worker_state`。
- `jobs.py`：投递、取任务、完成、失败重试（等 1 分钟、5 分钟、30 分钟再试，一共 4 次，之后进死信）、死信重试或忽略、30 天前完成的记录自动清理。同一种任务同时只有一个在排队或执行。
- `worker.py`：独立进程，每 5 秒看一次队列，同时最多执行 2 个任务，同一种任务不并行。
  - 由记忆服务启动时拉起并看护：意外退出 5 秒后重新拉起；记忆服务重启时一起重启，没做完的任务放回队列。
  - 日志在 `data/logs/worker.log`；任务开始、完成也写进 `auto_trigger.log`，Dashboard「系统日志」能看到。
  - 摘要、叙事、画像的生成逻辑还在 `main.py` 里，worker 目前直接导入复用；拆模块时再改。
- 记忆服务：
  - 定时检查只负责投递：提取每 10 分钟投递一次；摘要、叙事达到阈值才投递。
  - 「立即提取」「生成叙事」「重建画像」都改成投递任务。原来的状态接口格式不变，Dashboard 的调用方式不用改。
  - 手动「生成摘要」仍然当场生成，直接返回结果。
  - 新接口：`GET /jobs/stats`、`GET /jobs?status=`、`POST /jobs/{id}/retry`、`POST /jobs/{id}/dismiss`。
- 提取加了文件锁：worker 和手动运行 `extract_l1.py` 不会同时提取。
- crontab 里每 10 分钟的提取已删除，凌晨 3 点的备份保留。原来的 crontab 备份在 `~/crontab.bak.20261018`。
- Dashboard「记忆管线」页新增「后台任务」：worker 是否在线、正在执行什么、各状态数量、最近 30 个任务；失败的任务可以一键重试或忽略。

### 顺带发现并修复
- **近期摘要经常「生成失败」**：摘要用的 deepseek-v4-pro 是推理模型，思考也算在 max_tokens 里。原来只给 1000，经常思考完就没有额度写正文了。日志里出现过 716 次「生成失败」，只有思考得短的时候才成功。
  - 改成 6000；画像重建的分批提炼从 2500 改成 6000，汇总从 4000 改成 8000。
  - 以后再被截断，日志会写明原因。
  - 这是任务队列上线测试时发现的：失败的摘要任务出现在「等待重试」里，查下去才找到原因。

### 测试
- `tests/manual/test_jobs.py` 39 项全部通过：投递去重、退避时间、死信、重试和忽略、中断恢复、清理、并发上限、同类不并行、停止时放回队列、单实例锁。
- 用真实库的副本在 8011 端口起了一个临时记忆服务，测完已删除：
  - 自动提取、手动提取、生成叙事（没有新素材，跳过）都正常；
  - 摘要：修复前失败并自动排队重试，修复后 19 秒完成；
  - 不存在的任务类型直接进死信，重试、忽略接口正常；
  - `kill -9` 掉 worker，5 秒内被重新拉起，接着执行被中断的任务；
  - 正常停止时 worker 收尾退出，Dashboard 马上显示离线。
- 线上：重启后 worker 在线，定时检查投递的提取、手动「立即提取」都已完成；`phase0_smoke.py` 全部通过。

## 2026-10-18 · Phase 2 第一步：召回编排核心 + 影子模式

### 做了什么
- 新建 `app/recall/`，按方案第 8 章把「每一轮该想起什么」做成记忆服务里的一套核心，以后 API 模式和 Claude Code 模式共用：
  - 意图识别（规则）：回忆 / 事实 / 当下任务 / 情绪 / 寒暄 / 追问 / 普通；
  - 检索：向量 + 关键词（FTS5），RRF 融合；「然后呢」这类很短的追问，会拼上上一句和 AI 的回复再检索；
  - 精排：阿里云百炼的文本排序（默认 `qwen3.7-text-rerank`，和嵌入用同一个 key），超过 1.5 秒或出错就退回向量相似度；
  - 分层决策：强（精排分 ≥ 0.75，一定注入，最多 2 条）、中（0.5–0.75，30% 概率）、回忆模式（前 3 条，附原话）、无由来（5%，冷却 7 天）；寒暄不召回；被冷却拿掉的不拿更弱的来凑数；
  - 冷却只看新的投递账本 `injections`：同一会话最近 5 轮出现过的不再出现，中层冷却 24 小时；
  - 念头式卡片沿用网关现在的写法。
- 迁移 `004_recall`：召回轨迹 `recall_traces`、投递账本 `injections`。
- 新接口：`POST /compose/turn`、`GET /recall/traces`、`GET /recall/traces/{id}`、`GET /recall/stats`。
- **影子模式**：网关照旧用自己的浮现逻辑，同时每一轮把用户的话、上文和旧逻辑这一轮的决定发给 `/compose/turn`（不等结果，不影响回复）。新逻辑只记录、不注入，冷却也只看影子自己的记录。
  - `.env` 里 `GATEWAY_COMPOSE_SHADOW=off` 可以关掉；
  - 标题生成这类不进记忆的请求不发。
- Dashboard 新增「召回对比」：近 7 天的轮数、新旧两边各注入了多少轮、精排成功率、耗时；每一轮新旧两边各会想起什么。点开一行能看到候选、精排分、被冷却拿掉的，以及新逻辑会注入的文字。
