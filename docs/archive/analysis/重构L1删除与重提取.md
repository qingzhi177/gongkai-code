# 任务：重构记忆库 L1 删除/重提取机制（只改 memory-service 和 dashboard）

## 项目背景（先读代码再动手）
- 代码位置：services/memory-service/main.py（FastAPI 记忆服务）、services/dashboard/index.html（看板）
- 存储：SQLite 存 L0 消息(l0_messages)和 L1 记忆(l1_memories)；ChromaDB collection "l1_memories" 存 L1 向量，id 格式 "l1_{sqlite_id}"
- L1 两种来源：
  ① cron 从对话 L0 提取（extract_l1.py 的 save_l1），带 source_msg_id / conv_id / client
  ② AI 主动调 feel 工具记录（main.py 的 save_feel），conv_id=''、source_msg_id=NULL、client='ai_self'
- 批次锚点概念（重要）：source_msg_id 是"一次提取批次首条消息的 id"，
  main.py 的 _cascade_l1_on_version_switch 靠 active L1 的 source_msg_id 定位批次做联动（消息变更→作废该批 L1→重置该批消息 extracted=0→cron 重提取）

## 当前问题
DELETE /l1/{id}（main.py 约815行）只把 SQLite 标记 superseded，从不删 ChromaDB 向量 → 已删除记忆仍被 /search 的向量检索命中。
ai_self 感受无 conv_id/source_msg_id，只有这条删除路径，所以问题最明显。

## 目标方案（已确认，不要偏离）
1. L1 删除统一改为【硬删】：SQLite DELETE + ChromaDB delete
2. 新增 POST /l1/{id}/reextract 单条重提取：有关联 L0 的 L1 基于原文重新提取 → 生成新 L1 → 硬删旧 L1
3. ai_self（无 L0 关联）只能编辑/硬删；重提取接口对其返回错误
4. 编辑保持现有逻辑（改 content 重新生成向量并 update ChromaDB），补存在性校验
5. 看板加"重提取"按钮

## 改动清单

### A. services/memory-service/main.py
1. delete_l1（约815行）：UPDATE superseded → DELETE FROM l1_memories；SQLite 提交后再 l1_collection.delete(ids=[f"l1_{id}"])；ChromaDB 失败返回 warning 不回滚
2. _cascade_l1_on_version_switch（约420行）：把"UPDATE status='superseded'"改为 DELETE（批次定位逻辑不变，仍返回被删 L1 的 id 列表给调用方删向量）
3. delete_l0_message（约839行）：联动部分随第2点自动变硬删，其余不动
4. delete_l0_conversation（约878行）：L1 从 UPDATE superseded 改为 DELETE FROM l1_memories WHERE conv_id=? AND status='active'，仍先收集 id 再删向量
5. update_l1（约766行）：开头校验该 id 存在且 status='active'，否则返回 404/error（防止硬删后编辑已删 id 还返回 ok）
6. 新增 POST /l1/{memory_id}/reextract，行为必须满足：
   - 校验：L1 存在、status='active'、source_msg_id 非空；不满足返回 4xx（ai_self 的 source_msg_id 为 NULL，会自然被拒）
   - 取 L0 上下文：参考 get_l0_context 的查法（该 source_msg_id 前后各几条 active 消息）
   - 调 DeepSeek 提取：复用 extract_l1.py 的 EXTRACT_PROMPT 和 call_deepseek（import 或复制均可），DEEPSEEK_API_KEY 从环境变量读，并在 .env.example 补上；prompt 附带原 L1 的 content，要求基于原文重新提炼这一条，只输出一条
   - 新 L1 落库：source_msg_id 必须【沿用旧 L1 的值】（批次锚点，绝不能丢！），conv_id/client 沿用旧值，ts 用 L0 原文时间（参考 extract_l1.py 的 get_l0_ts），quote/event_type/tags/valence/arousal 用新提取结果
   - 写 ChromaDB：id=f"l1_{new_id}"，metadata 参照 save_l1
   - 硬删旧 L1：SQLite DELETE + ChromaDB delete
   - 顺序：SQLite 先提交，再删/写 ChromaDB；任一步失败 → 旧 L1 不删，返回 error（不允许出现"旧删了新没生成"的中间态）
   - 返回新 L1 的 id、content 等信息
7. /l1/list（约731行）：返回值里加 has_source 字段（source_msg_id IS NOT NULL）
8. /search（约312行循环内）：加一层兜底——从 ChromaDB 取到候选后，用 SQLite 校验该 L1 status='active'，不是则 continue（双保险，防历史残留向量）

### B. services/dashboard/index.html
- renderL1（约304行）：当 m.has_source 为 true 时显示"重提取"按钮；点击调 POST /l1/{id}/reextract，成功后刷新当前列表
- ai_self 不显示该按钮
