## 问题1：历史孤儿 L1 数据（对话已删但 L1/向量还在）

### 现象
删除某对话（如"四川省第十五届运动会"联网测试对话）后，L1 记忆页搜索"运动会"仍能搜到。

### 根因
这些对话是**在修复6 之前删除的**。老的 `DELETE /l0/conversation/{conv_id}` 只标记 L0 为 superseded，
没联动 L1 和 ChromaDB 向量。修复6 只对之后新删的对话生效，历史遗留数据需要一次性清理。

### 规模（2026-07-24 统计）
- 孤儿 L1（对话已删但 L1 还 active）：**14 条**，涉及 **12 个**已删对话
- 注：AI 自述 feel（`conv_id=''`）42 条不算孤儿，正常保留

### 排查/修复方案
写一次性清理脚本：找出 `status='active'` 但其 `conv_id` 下没有任何 active L0 的 L1
（排除 `conv_id=''` 的 AI 自述 feel），补标 superseded + 删 ChromaDB 向量。

判定 SQL 已验证：
```sql
SELECT l1.id, l1.conv_id FROM l1_memories l1
WHERE l1.status='active' AND l1.conv_id != ''
  AND NOT EXISTS (SELECT 1 FROM l0_messages l0 WHERE l0.conv_id=l1.conv_id AND l0.status='active')
```

## 问题2：新对话在 L0 原文页只显示 1 条消息【真实存储问题，非显示】

### 现象
最近创建的几个对话，Dashboard L0 原文页点开只显示 1 条消息。

### 排查发现（2026-07-24）
不是显示问题，是**存储问题**。最近的实时对话数据异常：
```
conv=unknown_47bfeb01 client=unknown 消息数=1 最后=2026-07-23 17:42:17
conv=unknown_d76b2b3f client=unknown 消息数=1 最后=2026-07-23 17:42:11
conv=unknown_7fec07d2 client=unknown 消息数=1 最后=2026-07-22 17:57:40
```
特征：
- conv_id 是 `unknown_` + 随机后缀，**每轮对话都生成新的**，没有稳定分组
- 每个对话只存了 **1 条**消息，role 都是 user（msg_idx=0）
- client=unknown

对比：导入的历史大对话 `unknown_fffce2bd` 有 1187 条，正常。

### 疑似根因
网关 `services/gateway/server.js` 的 `save_conversation` / conv_id 计算逻辑：
- conv_id 可能没从 Kelivo 请求里正确提取，fallback 成随机 `unknown_xxx`
- 只保存了 user 消息，没保存 AI 回复（或没按对话累积）

### 排查起点
- `server.js` 里 `computeConvId` / 保存对话到记忆服务的调用
- 记忆服务 `POST /l0/...` 存储接口，看 conv_id 和 msg_idx 怎么来的
